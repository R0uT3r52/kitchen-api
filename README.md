# Kitchen-API

RESTful бэкенд-сервис для платформы доставки еды, объединяющий покупателей и заведения-партнеры. Сервис предоставляет клиентский API для выбора заведений, просмотра меню и оформления заказов, а также защищенный партнерский API для интеграции кухонь (управление меню, стоп-листами и жизненным циклом заказов).

## Features

- **Клиентский API**:
  - Каталог активных заведений и получение актуального меню с учетом доступности (`is_available`).
  - Оформление заказа с валидацией позиций и серверным расчетом стоимости.
  - Просмотр деталей и истории заказов покупателя (`user_id`).
  - Отмена заказа клиентом до момента начала приготовления.
- **Партнерский API**:
  - Аутентификация заведений по закрытому API-ключу (`X-API-KEY`).
  - Синхронизация меню (`UPSERT`).
  - Поллинг поступающих заказов с фильтрацией по статусу.
  - Обновление статусов заказов по этапам приготовления.
- **Конечный автомат (FSM)**: строгий контроль переходов состояний заказа (`created -> accepted -> cooking -> ready -> completed`, `rejected`, `cancelled`) с защитой от race conditions.
- **Аудит изменений (Audit Trail)**: версионирование смены статусов заказа в таблице `order_events` для истории и аналитики.
- **Автономный микросервис партнера (`restaurant-example`)**: готовая симуляция кухни заведения с поллингом заказов, фоновой обработкой в горутинах и graceful shutdown.

## Architecture

Сервис спроектирован по принципам чистой архитектуры (Clean Architecture / Dependency Inversion): **Web** -> **Domain** <- **Repository**. Ядро бизнес-логики (**Domain**) полностью изолировано и определяет интерфейсы, которые реализует слой доступа к данным (**Repository** на `jackc/pgx/v5`), а слой **Web** (HTTP-хендлеры, DTO, middleware) обращается к сценариям домена.

> Подробные диаграммы доступны в каталоге [`docs/`](docs/):

> - [C4 Level 3 Component Diagram](docs/c4-level3.md)
> - [CJM покупателя](docs/cjm-user.md) и [CJM заведения](docs/cjm-restaurant.md)

## Database

Реляционная база данных спроектирована с учетом строгой ссылочной целостности и аудита изменений.

> Схема БД и описание полей находится в [docs/db.md](docs/db.md).

## API

Полная спецификация интерфейсов доступна в формате OpenAPI 3.0:  
**[OpenAPI Specs (api/openapi.yml)](api/openapi.yml)**

| Метод | Путь | Доступ | Описание |
| :--- | :--- | :--- | :--- |
| `GET` | `/health` | Публичный | Проверка работоспособности сервиса |
| `GET` | `/api/v1/restaurants` | Публичный | Список активных заведений |
| `GET` | `/api/v1/restaurants/{id}/menu` | Публичный | Меню заведения (доступные позиции) |
| `POST` | `/api/v1/orders` | Публичный (`user_id`) | Оформление нового заказа |
| `GET` | `/api/v1/orders/{id}` | Публичный | Детали и статус заказа |
| `GET` | `/api/v1/orders?user_id={id}` | Публичный (`user_id`) | Список всех заказов пользователя |
| `POST` | `/api/v1/orders/{id}/cancel` | Публичный (`user_id`) | Отмена заказа покупателем |
| `PUT` | `/api/v1/partner/menu` | `X-API-KEY` | Пакетный upsert меню и стоп-листа |
| `GET` | `/api/v1/partner/orders` | `X-API-KEY` | Заказы ресторана (фильтр по `status`) |
| `PATCH` | `/api/v1/partner/orders/{id}/status` | `X-API-KEY` | Обновление статуса заказа заведением |

## Tests

### Unit Tests
- **Domain Layer (`internal/domain`)**:
  - Table-driven тесты конечного автомата `CanTransition`.
  - Тестирование бизнес-правил через mock-репозиторий (валидация корзины, проверка доступности позиций, права отмены).
- **Web Layer (`internal/web`)**:
  - Тестирование HTTP-хендлеров через `httptest`.
  - Проверка валидации DTO, middleware авторизации по `X-API-KEY`, корректность статус-кодов (200, 201, 400, 401, 403, 404, 409).

### Integration Tests (Testcontainers)
- **Repository Layer (`internal/repository`)**:
  - Интеграционные тесты репозитория на базе контейнера PostgreSQL 16 с помощью **`testcontainers-go`** и автоматическим накатом SQL-миграций.
  - Проверка транзакционности: атомарное создание заказа, фиксация позиций и откат (`rollback`) при ошибках связей (`foreign key`).
  - Проверка цепочки событий аудита (`order_events`) и работы триггеров обновления (`updated_at`).

### Запуск тестов

```bash
# Запуск всех тестов (Unit + Integration через Testcontainers, требуется Docker)
go test -v ./...

# Запуск только unit-тестов
go test -v ./internal/domain/... ./internal/web/...

# Запуск интеграционных тестов репозитория
go test -v ./internal/repository/...
```

Проверка линтером (`golangci-lint`):
```bash
golangci-lint run ./...
```

## Run

Сервис и сопутствующие компоненты полностью контейнеризированы.

### 1. Подготовка окружения
Скопируйте шаблон переменных окружения:
```bash
cp .env.template .env
```

### 2. Запуск контейнеров
```bash
docker compose up --build
```

Команда запускает:
1. `PostgreSQL 16` с проверкой healthcheck.
2. Сервис миграций (`migrate`), применяющий схему БД и начальные сид-данные.
3. Основной сервис `kitchen-api` на порту `8080`.
4. Демонстрационный сервис партнера `restaurant-example`, который синхронизирует меню и начинает слушать заказы.

Для остановки:
```bash
docker compose down
```

## Demo

После запуска контейнеров можно проверить полный цикл оформления и обработки заказа через `curl`.

### 1. Просмотр ресторанов и меню
```bash
# Список активных ресторанов
curl -s http://localhost:8080/api/v1/restaurants

# Меню заведения #1
curl -s http://localhost:8080/api/v1/restaurants/1/menu
```

### 2. Создание заказа покупателем
```bash
curl -s -X POST http://localhost:8080/api/v1/orders \
  -H "Content-Type: application/json" \
  -d '{
    "user_id": "user_42",
    "restaurant_id": 1,
    "items": [
      {"menu_item_id": 1, "quantity": 1},
      {"menu_item_id": 2, "quantity": 2}
    ]
  }'
```

### 3. Workflow обработки заказа на кухне
В логах Docker (`docker compose logs -f restaurant-example`) отобразится автоматический цикл обработки поступившего заказа

### 4. Проверка статуса заказа
```bash
curl -s http://localhost:8080/api/v1/orders/1
```

### 5. Сценарий отмены клиентом (до готовки)
Клиент может отменить заказ, пока он в статусе `created` или `accepted`:
```bash
curl -s -X POST http://localhost:8080/api/v1/orders/1/cancel \
  -H "Content-Type: application/json" \
  -d '{"user_id": "user_42"}'
```
*Если кухня уже перевела заказ в статус `cooking`, API вернет `409 Conflict`.*

## Engineering decisions

### Ключевые архитектурные решения

1. **Серверная фиксация цен (Snapshot Pricing)**:
   Клиент отправляет только `menu_item_id` и `quantity`. Цены запрашиваются из БД на момент создания транзакции заказа и фиксируются в `order_items.unit_price_cents`. Это исключает возможность клиентской манипуляции суммами и гарантирует консистентность финансовой отчетности при последующих изменениях прайса рестораном.
2. **Строгая машина состояний и защита от гонок (FSM & Concurrency Control)**:
   Жизненный цикл заказа управляется строгой матрицей допустимых переходов (`CanTransition`). Любые конфликтующие действия (например, попытка клиента отменить заказ, когда кухня уже перевела его в `cooking`) отклоняются с кодом `409 Conflict`.
3. **Audit Trail (событийный лог `order_events`)**:
   Каждое изменение статуса фиксируется в отдельной таблице `order_events` в рамках единой транзакции со сменой статуса в `orders`. Это дает полную прозрачность истории выполнения заказа без перегрузки основной сущности.
4. **Модель взаимодействия через Polling**:
   Для взаимодействия кухни партнера с платформой выбран обычный polling (`GET /api/v1/partner/orders?status=created`). Для MVP был выбран именно этот метод, как наиболее быстрый для прототипирования. После MVP имеет смысл переписать на WebSocket или WebHook для упрощения интеграции и снижения нагрузки на сервис платформы.
5. **Транзакционный и идемпотентный Upsert меню**:
   Синхронизация позиций меню выполняется через запрос с ограничением `UNIQUE(restaurant_id, external_id)`. Это позволяет заведению безопасно повторно выгружать меню, обновляя цены и флаги стоп-листа без дублирования данных.
6. **Целочисленное хранение денежных сумм (Money Pattern)**:
   Все цены и суммы хранятся в целочисленном виде в минимальных неделимых единицах (`price_cents`, `unit_price_cents`, `total_price_cents` типа `bigint` / `int64`). Это классический паттерн (аналогично Stripe API), который полностью исключает ошибки округления чисел с плавающей точкой (`float`), обеспечивает быстрые арифметические операции и гарантирует строгую точность расчетов без накладных расходов сторонних библиотек.

### Допущенные упрощения (Scope MVP)
- **Идентификация клиентов**: в рамках MVP передается через параметр `user_id` без использования JWT.
- **Авторизация партнеров**: используется статический секретный ключ в HTTP-заголовке `X-API-KEY`, валидируемый через middleware.
